# 라이브러리 1,000개 성능 측정 — 2026-09-04 (A5)

## 결론

혼합 자산 1,000개(H.264+AAC 1초 클립 200개, 1×1 PNG 800개)를 실제 Chrome 152에서 가져와
정리·검색·소스 상태 검사·저장·복원을 쟀다. 가져오기(12초)와 새로고침 복원(0.6초)은 처음부터
쓸 만했고, 병목은 **1,000장 카드가 상태 변화마다 전부 다시 렌더되는 것**이었다. 카드를 memo
컴포넌트로 분리하고 화면 밖 카드의 레이아웃·페인트를 건너뛰게 하며(`content-visibility`),
소스 상태 훅이 누락 집합이 바뀔 때만 새 객체를 내도록 고친 뒤 검색 3배, 필터 2.3배,
소스 상태 검사 30배, 편집 후 저장 3.7배 빨라졌다. 필터 변경 346ms는 아직 눈에 띄는 수준이라
다음 단계는 가상화다.

## 방법

- 스크립트: `apps/web/scripts/bench-library.mjs` (Playwright + 설치된 Google Chrome, `next dev` 3000 포트).
  `node apps/web/scripts/bench-library.mjs --assets 1000 --videos 200 --out result.json`
- 측정: 가져오기(파일 선택 → 카드 1,000장), 라이브러리 행 JSON 길이, 검색창 입력 → "n개 중 m개" 갱신,
  길이 필터 변경 → 갱신, 창 포커스로 강제한 소스 상태 검사(`FileSystemFileHandle.getFile` 호출 수로 종료 판정),
  새로고침 → 카드 복원, 프로젝트 이름 변경 → "저장됨" 배지, `performance.memory.usedJSHeapSize`.
- 환경: Apple Silicon Mac, Chrome 152, 개발 서버(turbopack). 프로덕션 빌드는 조금 더 빠를 수 있다.

## 결과

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 가져오기 1,000개 | 13335 ms (13.3 ms/자산) | 11920 ms (11.9 ms/자산) |
| 저장된 프로젝트 JSON | 6.9 MB | 6.9 MB |
| 검색 키 입력 → 개수 표시 | 166 ms | 54 ms |
| 필터 변경 → 개수 표시 | 804 ms | 346 ms |
| 소스 상태 검사(창 포커스, 1,000개) | 15504 ms · 파일 열기 2917회 | 521 ms · 파일 열기 1000회 |
| 새로고침 → 카드 1,000장 | 790 ms | 607 ms |
| 이름 변경 → 저장됨 배지 | 256 ms | 69 ms |
| JS 힙(가져오기 직후 / 새로고침 뒤) | 243.6 MB / 138.5 MB | 155.2 MB / 233.4 MB |

수정 전 소스 상태 검사에서 파일 열기가 2,917회로 잰 것은 가져오기 중 시작된 첫 검사가 아직 끝나지
않은 상태에서 포커스 검사가 겹친 탓이다. 검사 자체(1,000회 열기)는 0.5초면 끝나고, 15초는
검사 결과가 8개씩 반영될 때마다 카드 1,000장이 다시 렌더된 비용이었다.

## 남은 병목과 다음 단계

- 필터 변경 346ms: 800장 카드를 DOM에서 떼는 비용. 날짜 그룹 단위 가상화(`@tanstack/react-virtual` 또는
  IntersectionObserver로 보이는 그룹만 렌더)가 다음 후보.
- 저장된 프로젝트 JSON 6.9MB(썸네일·필름스트립 data URL 포함): 내용이 바뀔 때마다 300ms 디바운스로 전체를
  다시 직렬화한다. 1,000개에서는 69ms라 참을 만하지만 3,000개부터는 썸네일을 프로젝트 문서 밖 캐시로
  옮겨야 한다.
- 힙 150~230MB: data URL 썸네일이 대부분. 위 캐시 분리와 함께 줄어든다.
- 데스크톱 참조 파일에서는 소스 상태 검사 1회가 lease + `media://` 요청이라 브라우저 OPFS보다 비싸다.
  포커스 검사 10초 제한은 유지하되 실기기 도그푸딩에서 다시 잰다.
