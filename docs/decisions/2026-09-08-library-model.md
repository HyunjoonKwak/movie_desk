# D2: 라이브러리 모델 — 사용자가 무엇을 먼저 정하는가

상태: **구현 완료 — 2026-09-10** · 승인 2026-09-10 · 작성 2026-09-08

## 질문

파이널컷은 **보관함(Library)을 먼저 만들고** 그 안에 이벤트와 프로젝트를 넣는다.
Movie Desk는 프로젝트를 열고 **곧바로 미디어를 가져온다.** 담을 그릇을 정하는 단계가 없다.

이 차이가 의도된 것인지, 아니면 아직 결정하지 않은 것인지 정한다.

## 파이널컷이 혼동을 주는 지점

파이널컷은 첫 실행에서 사용자에게 세 가지를 한꺼번에 요구한다.

1. 보관함을 어디에 만들 것인가 (내장 디스크? 외장? 나중에 옮길 수 있나?)
2. 미디어를 보관함 안으로 **복사**할 것인가, 제자리에서 **참조**할 것인가
3. 이벤트를 어떻게 나눌 것인가

세 질문 모두 **아직 아무 작업도 안 해본 시점에** 나온다. 그래서 답할 근거가 없다.
잘못 고르면 나중에 수백 기가를 옮겨야 하고, 그 사실조차 한참 뒤에 안다.

혼동의 원인은 보관함이라는 개념 자체가 아니라 **결정 시점**이다.
사용자가 판단할 정보를 갖기 전에 되돌리기 비싼 선택을 강요하는 것.

## 우리가 이미 가진 것 (2026-09-08 코드 확인)

Movie Desk에는 파이널컷의 보관함에 해당하는 것이 **이미 있다. 다만 보이지 않는다.**

데스크톱 카탈로그에 `source_roots` 테이블이 있다
(`apps/desktop/src/catalog-schema.cjs`). 각 행은 `kind`가 `local`·`removable`·`network`이고
볼륨 UUID와 볼륨 상대경로를 가진다. 모든 미디어 자산은 `root_id`로 이 행을 참조한다.

그리고 D1 결정(`2026-09-03-local-media-storage.md`)이 정한 원칙이 있다.

> 사용자가 선택한 사진·영상 원본은 **제자리에서 참조**한다.
> 가져오기는 기본적으로 원본 복사·이동·수정을 하지 않는다.

즉 우리 모델은 이렇다.

**사용자의 기존 폴더가 곧 root다. 새로 만들 그릇이 없다.**

파이널컷의 세 질문 중 1번과 2번은 우리에게는 **질문 자체가 성립하지 않는다.**
원본은 원래 있던 자리에 그대로 있고, 우리는 그 위치를 기억할 뿐이다.

## 결정

**보관함을 먼저 만들게 하지 않는다. 대신 참조하는 위치를 항상 보이게 한다.**

파이널컷의 순서를 따르지 않는 이유는 개념을 몰라서가 아니라,
그 순서가 만드는 혼동을 우리 구조에서는 겪을 필요가 없기 때문이다.

### 사용자가 실제로 겪는 흐름

| 시점 | 사용자가 하는 것 | 우리가 하는 것 |
| --- | --- | --- |
| 첫 실행 | 없음 | 아무것도 묻지 않는다 |
| 가져오기 | 폴더나 파일을 고른다 | 그 위치를 root로 자동 등록한다 |
| 편집 중 | 없음 | 어느 위치를 참조 중인지 볼 수 있다 |
| 드라이브 분리 | 없음 | 어느 root가 오프라인인지 이름으로 알린다 |
| 이사·백업 | 필요할 때 | 무엇을 복사해야 하는지 알려준다 |

### 반드시 지킬 것

1. **첫 경로에 질문을 추가하지 않는다.** 가져오기 전에 위치를 묻지 않는다.
   폴더를 고르는 행위가 곧 root 선택이다.
2. **참조 위치는 언제나 조회 가능해야 한다.** 사용자가 "내 원본이 어디 있지"라고
   물었을 때 답이 화면에 있어야 한다.
3. **root는 이름을 가진다.** `/Volumes/T7/2026 여행` 이 아니라 사용자가 알아보는 이름.
   기본값은 폴더 이름, 사용자가 바꿀 수 있다. 드라이브가 빠졌을 때
   "T7의 2026 여행 폴더가 연결되지 않았습니다"라고 말할 수 있어야 한다.
4. **복사를 원하는 사용자를 막지 않는다.** 외장에서 내장으로 옮겨 작업하고 싶은
   경우가 실제로 있다. 다만 **기본값이 아니고, 명시적 행동이며, 원본을 지우지 않는다.**
5. **프로젝트는 root를 소유하지 않는다.** 여러 프로젝트가 같은 root를 공유한다.
   파이널컷의 보관함처럼 프로젝트가 미디어를 가두지 않는다.

### 모으기(consolidate) — 제공한다

사용자 결정(2026-09-10): 복사 기능을 제공한다. 다만 **처음에 묻지 않고, 나중에 쓴다.**

우리는 파일을 경로가 아니라 내용으로 식별하므로(크기 + quick hash + 필요 시 full hash)
나중에 모으는 것이 처음에 정하는 것보다 쉽다. 파이널컷은 이 선택을 첫 실행에 강요하고
마음이 바뀌면 보관함 형식 안에 갇힌 원본을 다시 꺼내야 한다. 우리는 처음에 아무것도
가두지 않으므로 이 작업이 단순한 복사 + 검증 + 참조 교체가 된다.

절차는 반드시 이 순서다.

1. 새 위치로 **복사**한다. 이동이 아니다.
2. 사본이 원본과 바이트 단위로 같은지 **검증**한다.
3. 검증된 것만 참조를 새 위치로 **교체**한다.
4. **원본은 지우지 않는다.** 삭제는 검증 후 사용자가 따로 결정하는 별개 행동이다.

이동으로 구현하면 중간 실패 시 원본도 사본도 온전하지 않은 상태가 생긴다.

범위는 두 가지다.

- **프로젝트가 실제로 쓰는 원본만 모으기** — 아카이브·인계용.
- **특정 root 아래 전부 옮기기** — 외장→내장, 드라이브 교체용.

**사용 구간만 잘라 모으는 것은 첫 버전에서 제외한다.** 여유분을 버리므로 나중에 트림을
늘릴 수 없다. 되돌릴 수 없는 작업이라 넣더라도 명시적 opt-in 이어야 하고 무엇을
잃는지 분명히 알려야 한다.

### 하지 않는 것

- 첫 실행에 보관함 생성 마법사를 넣지 않는다.
- 프로젝트를 만들 때 저장 위치를 묻지 않는다.
- 원본을 앱 전용 폴더로 기본 복사하지 않는다.
  (현재 웹 경로는 앱 저장소로 복사한다. 이것은 D1이 폐기 대상으로 지정한 이전 모델이다.)
- 이벤트에 해당하는 중간 계층을 만들지 않는다. 태그·평점·컬렉션이 그 역할을 한다.

## 순서 (2026-09-10 사용자 결정)

**제자리 참조 전환을 B'6(프록시·캐시·워커 측정)보다 먼저 진행한다.**

근거: B'6 은 프록시와 캐시를 다루는데, 원본이 앱 저장소에 복사돼 있느냐 제자리에
있느냐가 캐시 키·수명·용량 설계에 직접 영향을 준다. 순서가 반대면 B'6 을 두 번 한다.
그리고 수백 기가 규모 실제 푸티지는 복사 방식으로는 시작 자체가 어렵다.

진행 중인 B'5(중첩 시퀀스)의 6B·6C 는 먼저 끝낸다. 지금 중첩 시퀀스는 저장·렌더·
재생이 모두 되지만 **사용자가 만들 방법이 없어** 도달 불가능한 상태다. 6B 가
들어가야 그 투자가 사용 가능한 기능이 된다. 중간에 멈추면 그 상태로 남는다.

root 를 보여주는 UI 는 제자리 참조 전환 배치에 포함한다. 그 전까지는 원본이 앱
저장소로 복사되므로 보여줄 대상 자체가 없다.

## 구현 (2026-09-10 완료)

| 약속 | 어디에 |
| --- | --- |
| 1. 첫 경로에 질문 없음 | 가져오기가 폴더 선택을 root 선택으로 삼는다 (`6a94809`) |
| 2. 참조 위치 조회 | 우측 패널의 원본 위치 탭 (`20d9b3a`) |
| 3. root 이름 + 오프라인 표시 | `bdb92c7` — 이름 변경, 연결 안 됨 배지와 안내 |
| 4. 복사를 막지 않음 | 모으기 (`276837f`, `8249bdf`) |
| 5. 프로젝트가 root를 소유하지 않음 | root는 카탈로그 소유, 프로젝트는 asset id 만 참조 |

3번에서 배운 것: 이름 자체는 편의지만 **오프라인 표시가 실제 문제 해결**이다.
사용자가 왜 재생이 안 되는지 아는 수단이기 때문이다. 이름은 그 안내를
읽을 수 있게 만드는 보조다. 그래서 오프라인 표시를 먼저 넣었다.

한 번도 확인한 적 없는 상태와 연결이 끊긴 상태를 구분한다.
확인한 적 없는 것을 문제로 보고하면 사용자가 없는 문제를 쫓게 된다.
연결이 끊긴 위치에서는 모으기 버튼을 감춘다 — 누르면 전부 실패하고
사용자는 이유를 볼 수 없다.

## 미해결

- **웹과 데스크톱의 차이를 사용자에게 어떻게 설명하는가.** 웹은 브라우저 제약으로
  제자리 참조가 불가능하다. `apps/web`은 개발 미리보기이지 별도 제품이 아니라는 것이
  D1의 입장이지만, 사용자가 둘 다 쓰게 되면 설명이 필요하다.
- **root가 사라진 뒤 오래 지난 경우.** 볼륨 UUID로 찾지 못하고 사용자도 기억하지
  못하는 상태. 재연결 순서의 마지막 단계 UX가 아직 정해지지 않았다.
- Photo Desk와 root 개념을 어디까지 공유할 것인가. D1은 경로 의미는 공유하되
  SQLite 파일은 공유하지 않는다고 정했다.
