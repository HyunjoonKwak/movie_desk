# B′5 Phase 6C — 시퀀스 피치 보존 옵트인

작성 2026-09-10. B′5 중첩 시퀀스의 마지막 단계.

## Phase 5 가 이것을 미룬 이유

Phase 5 는 시퀀스 경계를 varispeed 로만 두고 저장 필드를 미뤘다.
근거는 **필드와 토글이 함께 들어가야 끝에서 끝까지 검증된다**는 것이었다.
설정할 UI 없이 영속 필드를 먼저 넣으면 죽은 데이터에 마이그레이션 위험만 얹는다.
그리고 그 표면은 Phase 1+7 이 리뷰 5라운드를 쓴 곳이다.

## 계약

`MediaClip.preservePitch` 와 **같은 계약**이다. 옵트인이고, 필드가 없는 문서는
컴파운드가 늘 가지고 있던 varispeed 를 그대로 유지한다.

기본값을 varispeed 로 둔 것은 일관성 때문이다. 미디어 클립도 기본이 varispeed 이므로,
"미디어는 피치가 보존되는데 컴파운드로 감싸면 갑자기 varispeed" 같은 불일치가 없다.

## 합성 순서 — Phase 5 가 기록한 설계를 그대로 따른다

자식이 **먼저 믹스다운**된 뒤 그 결과에 B′2 시간축 변환을 적용한다.
배율을 곱하는 것이 아니라 순서대로 합성된다.

그래서 피치가 보존된 자식 위에 부모 속도가 얹혀도 자식의 보존이 무효가 되지 않는다.
Phase 5 가 이것을 수치로 확인했다 — 보존된 440 Hz 자식에 2배속 부모를 얹으면 880 Hz.

## 시간축 변환기 계약을 좁힌 것

`StretchRequest.clip` 이 `MediaClip` 으로 선언돼 있었다. 그런데 변환기가 실제로 읽는
필드를 세어 보니 다섯 개뿐이었다 — `trimIn`, `trimOut`, `speed`, `keyframes`,
`preservePitch`. **파일 기반이라는 사실은 쓰지 않는다.**

그래서 계약을 "소스 구간을 가진 클립"으로 넓혔다. 컴파운드는 자식이 이미 믹스다운된
상태로 도달하므로 파일이 없어도 같은 계약을 만족한다.
`assetId` 를 요구하던 것은 실제 의존이 아니라 과하게 좁은 선언이었다.

## UI

기존 속도 패널의 피치 토글을 시퀀스에도 적용했다. 새 컨트롤을 만들지 않았다 —
사용자에게는 같은 개념이고 같은 자리에 있어야 한다.

상태 힌트(렌더링 중·지원 범위 밖·폴백)는 미디어 전용으로 남겼다.
그 진단은 파일 디코딩 경로에서 나오는 것이라 컴파운드에는 해당하지 않는다.

## 마이그레이션 검증

Phase 1+7 이 다섯 라운드를 쓴 표면이므로 새 필드를 검증 없이 넣지 않는다.

- 필드가 없던 문서가 그대로 열리고 varispeed 를 유지한다.
- JSON 내보내기·가져오기 왕복에서 값이 남는다.
- CRDT 쓰기·읽기 왕복에서 값이 남는다.
- 한쪽 복제본만 켠 상태로 병합해도 값이 살아남는다.
- 불리언이 아닌 값은 저장되지 않고 거부된다.
