# 스파이크: HEIC/HEIF 정지 이미지 처리 (D3 / B10)

작성 2026-09-03 · 담당 Codex · 재현:
`scripts/spikes/heic-capability.cjs`, `scripts/spikes/heic-probe.html`

## 질문

Movie Desk의 macOS Electron 런타임이 아이폰 HEIC 원본을 직접 표시할 수 있는지,
그렇지 않다면 어떤 네이티브 경계에서 미리보기와 메타데이터를 만들어야 하는지
확인한다. 테스트는 640×360 PNG를 macOS `sips`로 HEIC로 변환한 12,227바이트
fixture와, 같은 파일에서 만든 240×135 JPEG 대조군으로 했다.

```sh
ffmpeg -f lavfi -i "testsrc2=size=640x360:rate=1" -frames:v 1 source.png
sips -s format heic source.png --out sample.heic
sips -Z 240 -s format jpeg sample.heic --out sample-thumb.jpg
cd apps/desktop
pnpm exec electron ../../scripts/spikes/heic-capability.cjs sample.heic sample-thumb.jpg
```

## 결과

환경: macOS 26.5.2, Electron 43.1.1 / Chrome 150.

| 경로 | HEIC | JPEG 대조군 |
| --- | --- | --- |
| `ImageDecoder.isTypeSupported` | `false` | `true` |
| `createImageBitmap(Blob)` | `InvalidStateError` | ✅ 240×135 |
| `<img src={blobUrl}>` | 로드 실패 | ✅ 240×135 |
| macOS ImageIO (`sips`) 메타 | ✅ 640×360, sRGB | 해당 없음 |
| macOS ImageIO (`sips`) JPEG 미리보기 | ✅ 240×135 | 해당 없음 |

앱의 `app://` 프로토콜은 현재 `.heic`를 `application/octet-stream`으로 제공한다.
하지만 테스트에서 Blob 타입을 명시적으로 `image/heic`로 강제해도 두 렌더러 경로가
모두 실패했다. MIME 매핑만 추가해서 해결되는 문제가 아니다.

## 결론

**HEIC는 Electron 렌더러에서 직접 디코드하지 않고 macOS ImageIO 경계에서 처리한다.**
원본 파일은 그대로 보존하고, 렌더러에는 색상 프로파일과 방향을 적용한 JPEG 또는 PNG
프리뷰를 준다. 촬영 시각·GPS·방향·카메라 정보 역시 같은 ImageIO 소스에서 추출한다.

`sips`는 기능 확인과 초기 연결에는 충분하지만 최종 대량 라이브러리 경로로 고정하지
않는다. Photo Desk는 파일마다 `sips` 프로세스를 띄우던 구조를 ImageIO 인프로세스 FFI로
교체했다. Movie Desk도 아래와 같이 교체 가능한 경계를 먼저 만들고, 대량 가져오기 전에
같은 ImageIO 구현을 작은 네이티브 helper로 재사용하는 것이 맞다.

## B10 설계안 (Claude와 교환용)

1. **원본 보존.** HEIC 원본은 사용자 파일의 디스크 참조를 authoritative source로
   유지한다. 캐시에는 렌더링용 프리뷰와 썸네일만 둔다. HEIC를 가져오면서 JPEG 원본으로
   바꾸거나 중복 복사하지 않는다.
2. **교체 가능한 데스크톱 API.** Electron preload에 `inspectImage(path)`와
   `renderImagePreview(path, maxPx)` 형태의 좁은 IPC 계약을 둔다. 1차 구현은 `sips`로
   검증할 수 있지만, B12의 폴더/대량 가져오기 전에 Photo Desk의 ImageIO FFI와 같은
   인프로세스 helper로 교체한다. 렌더러는 구현 방식을 알지 않는다.
3. **메타데이터.** helper 결과에 원본 픽셀 크기, EXIF orientation, 촬영 시각, GPS,
   카메라/렌즈, 색상 프로파일 식별자를 포함한다. 프리뷰는 orientation과 ICC 변환이
   적용된 상태로 만들고, 원본 메타데이터는 `MediaAsset`에 별도로 보존한다.
4. **프리뷰 계층.** 미디어 빈은 240px 썸네일, 소스 뷰어와 컴포지터는 화면 크기에 맞춘
   상위 프리뷰를 쓴다. 둘 다 원본 fingerprint를 키로 한 디스크 캐시이며 필요하면
   재생성한다. 내보내기는 최종 크기에 맞는 프리뷰를 새로 만들거나 ImageIO 원본 디코드를
   요청해 품질 저하의 누적을 막는다.
5. **실패 안내.** 손상 파일, 권한 상실, 지원하지 않는 HEIF 변형을 서로 다른 오류로
   분류해 B9의 파일별 복구 UI에 전달한다. 원본 경로 재연결과 캐시 재생성을 구분한다.
6. **검증.** CI에는 재배포 가능한 소형 HEIC fixture와 메타데이터/회전 단위 테스트를
   둔다. 실제 아이폰 fixture(HDR gain map, Live Photo 짝, GPS 포함)는 저장소에 넣지
   않고 도그푸딩 세트로 확인한다. Electron HEIC 직접 디코드 실패는 capability smoke로
   남겨 플랫폼 변경을 감지한다.
7. **웹 개발 빌드.** HEIC를 직접 디코드할 수 없는 브라우저에는 “macOS 앱에서 지원”을
   표시한다. 웹 호환을 위해 WASM 디코더를 제품 핵심 경로에 추가하지 않는다.

## D1과의 결합 조건

B10을 현재 OPFS 복사 구조에 바로 붙이면 HEIC 원본과 프리뷰를 모두 앱 저장소에 복제하게
된다. 먼저 D1에서 `sourceRef`(사용자 원본)와 `cacheRef`(재생성 가능 산출물)를 분리하고,
안정적인 asset ID와 재연결 규칙을 확정해야 한다. 이 계약이 B10과 B12의 선행 조건이다.
